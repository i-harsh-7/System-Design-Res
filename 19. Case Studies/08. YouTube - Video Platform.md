# Design: YouTube (Video Sharing Platform)

## Problem Statement

Build a video platform where users can upload videos, which are transcoded to multiple formats and resolutions, then streamed to viewers globally at scale. The system must handle 500 hours of video uploaded every minute, serve billions of daily video views, support comments, likes, subscriptions, and surface relevant videos through recommendations and search.

## Why This System is Interesting

YouTube combines two fundamentally different systems: an upload/processing pipeline and a read-heavy streaming platform. The upload side is an async batch-processing problem — transcode video to 8+ formats, extract thumbnails, run content moderation, index for search. The streaming side is an extreme read-heavy CDN problem — a single viral video might be requested 100 million times in 24 hours. Counting views accurately at this scale, without a database lock on every view event, is a classic system design challenge. User-generated content also means the read/write ratio is much more balanced than Netflix (which is read-only).

## Functional Requirements

- Users can upload videos (any resolution, up to 12 hours long, up to 256 GB)
- Videos are transcoded to multiple resolutions (360p, 480p, 720p, 1080p, 4K) and formats (H.264, VP9, AV1)
- Video streaming with adaptive bitrate (ABR) — quality adjusts to viewer's connection speed
- View count, likes, dislikes, comments on each video
- Subscriptions — users subscribe to channels, see uploads in feed
- Video search by title, description, tags
- Recommendations — suggested videos sidebar and homepage feed
- Chapters/timestamps, closed captions

## Non-Functional Requirements

- Upload-to-available latency: < 5 minutes for videos under 1 hour
- Streaming latency: < 2 seconds to first frame
- View count eventual consistency acceptable (off by < 0.1% is fine)
- Read/write ratio for video content: ~10,000:1 (most users only watch)
- 99.9% availability for video playback
- CDN cache hit rate > 95% for popular content

## Capacity Estimation

**Upload throughput:**
```
500 hours of video/minute = 8.33 hours/second
At 2 Gbps average bitrate per hour of raw video:
8.33 hours × 3600 seconds × 2 Gbps = ~60 Gbps incoming upload bandwidth
```

**Transcoding output:**
```
Each video → 8 quality levels × average 4 compression ratio = 2x total output
60 Gbps input → ~120 Gbps transcoded output to store
Per day: 500 hours × 60 min = 30,000 hours of video/day
```

**Storage:**
```
1 hour of 1080p H.264 ≈ 4 GB
Average video: 10 minutes = 0.67 GB per quality level × 8 levels ≈ 5 GB total per video
500 hours/min = 30,000 min/min of content = 3,000 new videos/min (avg 10 min each)
3,000 × 5 GB = 15 TB of new video storage per minute
Per year: ~7.9 exabytes of video stored
```

**View volume:**
```
YouTube: ~1B hours watched per day
Average video: 7 minutes = 0.117 hours
1B hours / 0.117 hours = ~8.5B video sessions/day
8.5B / 86,400 sec = ~98,000 video streams/sec average
Peak: 500,000 concurrent streams
```

**View count events:**
```
8.5B view events/day / 86,400 = ~100,000 view events/second
```

```
POST /v1/videos/{video_id}/views

```

**Feed/Search:**

```
GET /v1/feed/subscriptions?page_token={token}
Response: { videos: [...], next_page_token }

GET /v1/search?q={query}&filter={category}&sort={relevance|date|views}
Response: { results: [{video_id, title, thumbnail, channel, view_count, duration}], total }
```

## Core Components Deep Dive

### Video Upload and Transcoding Pipeline

When a user uploads a video:

1. **Upload Service** receives chunks, assembles raw video in object storage
2. Publishes a `video.uploaded` event to Kafka with `{video_id, raw_storage_path}`
3. **Transcoding Workers** (FFmpeg running on GPU instances) pick up the job:
   - Transcode to 8 resolution/quality variants in parallel
   - Package as MPEG-DASH (`.mpd` manifest + `.m4s` segments of 2-10 seconds each)
   - Upload segments to object storage under structured paths: `videos/{video_id}/{quality}/seg_{n}.m4s`
4. **Thumbnail Generator** extracts frames at multiple timestamps, runs through a visual quality classifier
5. **Content Moderation** ML pipeline checks audio, video, and speech-to-text against policy violations
6. **Metadata Writer** marks the video as `READY` once transcoding + moderation complete

**Why async?** Transcoding a 1-hour 4K video takes 30–60 minutes even with GPU acceleration. The upload API returns immediately with `status: "processing"` — the user is notified via push when the video is live.

**Adaptive Bitrate Streaming (ABR):** MPEG-DASH segments are small (4 seconds each). The player downloads the manifest, starts with a quality level matching the current bandwidth estimate, and continuously adjusts. If the connection degrades, it seamlessly switches from 1080p to 480p by requesting the next segment at lower quality — no buffering.

### View Count with HyperLogLog and Redis

Naive view counting: `UPDATE videos SET view_count = view_count + 1 WHERE id = ?`

At 100,000 views/second, this creates a hot row contention problem. The solution:

**Step 1 — In-memory counter (Redis):**
```
INCR view_count:{video_id}
```
Redis processes millions of INCRs per second with no lock contention. View counts are written to Redis on every view event.

**Step 2 — Periodic flush to DB:**
A background job every 30 seconds reads Redis counters and batch-writes to the database. The DB view count may lag by up to 30 seconds, which is imperceptible to users.

**Step 3 — Unique view counting with HyperLogLog:**
To prevent a single user from inflating counts (watching a video 1000 times), YouTube only counts unique viewers. HyperLogLog (HLL) is a probabilistic data structure that estimates unique cardinality with < 1% error using only 12 KB of memory — regardless of how many unique viewers there are.

```
PFADD unique_viewers:{video_id} {user_id or IP}
PFCOUNT unique_viewers:{video_id}  → approximate unique count
```

HLL cannot return which viewers it's seen, only an estimate of how many — this is sufficient for display purposes and uses negligible memory.

### CDN Strategy for Popular Videos

Videos are stored in object storage (origin). The CDN edge network has 100+ global Points of Presence (PoPs). When a viewer requests a video segment:

1. Request hits nearest CDN edge node
2. Edge checks: is segment cached? → Serve it (cache hit, < 5ms)
3. Cache miss: fetch from origin storage, cache locally, serve to client

For viral videos, the cache hit rate approaches 99.99% — essentially zero origin traffic. For long-tail videos (uploaded 5 years ago, watched rarely), the CDN doesn't cache them — the origin serves directly.

YouTube pre-warms CDN caches for scheduled content (a new music video from a top artist). The system detects the upload is from a high-subscriber channel and proactively pushes video segments to edge nodes before the video goes live.

## Database Design

### Video Metadata (Bigtable / Spanner)

```
Table: videos
Key:    video_id (UUID)
Columns:
    meta:title          VARCHAR(100)
    meta:description    TEXT
    meta:channel_id     UUID
    meta:status         ENUM(uploading, processing, ready, removed)
    meta:visibility     ENUM(public, private, unlisted)
    meta:duration_sec   INTEGER
    meta:category       VARCHAR(50)
    stats:view_count    BIGINT      (periodic flush from Redis)
    stats:like_count    BIGINT
    stats:comment_count BIGINT
    storage:manifest_url  VARCHAR(512)
    storage:thumbnail_url VARCHAR(512)
    ts:published_at     TIMESTAMP
    ts:created_at       TIMESTAMP
```

### Comments (MySQL, sharded by video_id)

```sql
CREATE TABLE comments (
    comment_id  BIGINT AUTO_INCREMENT PRIMARY KEY,
    video_id    CHAR(11) NOT NULL,
    author_id   BIGINT NOT NULL,
    parent_id   BIGINT,              -- NULL for top-level, set for replies
    content     TEXT NOT NULL,
    like_count  INT DEFAULT 0,
    created_at  DATETIME DEFAULT NOW(),
    is_deleted  BOOLEAN DEFAULT FALSE,
    INDEX idx_video_top (video_id, parent_id, like_count DESC),
    INDEX idx_video_recent (video_id, parent_id, created_at DESC)
) ENGINE=InnoDB;
```

Sharded by `video_id % N_shards`. Replies are co-located with parent comment's shard.

### Search Index (Elasticsearch)

```json
{
    "video_id": "abc123",
    "title": "How to cook pasta",
    "description": "In this tutorial...",
    "tags": ["cooking", "pasta", "Italian"],
    "channel": "ChefMario",
    "category": "Food",
    "published_at": "2026-01-15T10:00:00Z",
    "view_count": 1500000,
    "duration_sec": 847

```

The `view_count` is included in the index to boost ranking of popular results. The index is updated asynchronously from the Kafka view-count stream — search rankings reflect recent popularity.

## Scaling Strategy

**Transcoding:** Horizontally scale FFmpeg workers. Each worker is a stateless consumer of the transcoding Kafka queue. Scale out GPU instances during upload peak hours (typically evenings). Use spot/preemptible instances for cost efficiency.

**Metadata reads:** Bigtable scales to millions of rows/second natively. Read-heavy workloads are supplemented by Redis caching for hot videos (front page, trending).

**Comment loading:** Comments are read-heavy (millions see a popular video's comments). Redis caches the top 50 comments per video. Comment writes (new comments, likes) are queue-buffered.

**Search:** Elasticsearch cluster scales horizontally. The index is replicated across 3 shards with 2 replicas each — read traffic is load-balanced across replicas.

## Key Bottlenecks and Solutions

| Bottleneck | Root Cause | Solution |
|---|---|---|
| Transcoding queue backup | Viral upload spike (celebrities) | Priority queue — large channels get faster transcoding; auto-scale GPU fleet |
| View count hot key in Redis | Single viral video gets 1M views/sec | Redis cluster with consistent hashing; local in-process counters that flush to Redis every second |
| CDN cache miss for new video | Segments not yet cached on edge | Pre-warm CDN for high-subscriber channels; origin can handle uncached long-tail |
| Comment load on viral video | 50M people opening comments simultaneously | Paginate aggressively; cache top comments; lazy-load replies; rate-limit comment writes |
| Search index lag | Indexer cannot keep up with 500 uploads/min | Prioritize metadata indexing (fast); defer description/caption indexing (slower); eventual consistency acceptable |

## Trade-offs Made

**Approximate view counts vs. exact:** HyperLogLog introduces < 1% error in unique view counting. This is acceptable — view counts are a social signal, not a financial ledger. Exact counting would require a distributed set membership data structure that scales poorly.

**Eventual consistency for recommendations vs. real-time:** The recommendation model runs on batch data (typically updated every hour). A video uploaded an hour ago won't appear in recommendations immediately. This is acceptable — freshness is sacrificed for recommendation quality (batch model is more accurate than real-time).

**MPEG-DASH segments vs. progressive download:** Segment-based streaming requires more HTTP requests but enables seamless quality switching. Progressive download is simpler but wastes bandwidth if a user watches 10% of a video (you've buffered 100%).

**Separate upload and serving infrastructure:** Uploads and playback are on completely separate infrastructure. This prevents a massive upload surge (new year's eve uploads) from affecting playback quality for viewers.

## Real-World: How YouTube Does It

YouTube uses **Borg** (Google's container orchestration, precursor to Kubernetes) to manage transcoding workers. Video storage uses **Google Cloud Storage** with regional replication. YouTube's CDN is Google's own network — one of the world's largest — with edge nodes in ISPs and data centers globally. View counting uses a **sharded counter** system backed by Bigtable, with counts aggregated in memory before periodic DB writes. The recommendation system uses a two-tower deep learning model: one tower encodes videos, one encodes users, and nearest-neighbor search in the embedding space finds relevant recommendations. YouTube's search is powered by a customized version of Google Search infrastructure.

## Interview Discussion Points

- **How do you handle a video that goes viral immediately?** CDN pre-warming for high-subscriber channels; Redis view counter handles write spikes natively; no DB bottleneck since counts flush asynchronously.
- **How does adaptive bitrate work?** MPEG-DASH manifest lists segment URLs at each quality. Player measures download speed of each segment, requests next segment at the highest quality achievable within time budget.
- **Why not just upload to S3 and serve from there?** S3 charges per-request and has limited global distribution. A CDN reduces origin load by 99%+ for popular content and puts video segments physically closer to viewers.
- **How do you handle copyright violations?** Content ID: upon upload, audio/video fingerprints are extracted and compared against a database of copyrighted content. If matched, the video can be monetized by the copyright holder or taken down.
- **How do you transcode 500 hours/minute?** Parallelism: each video is split into GOP (Group of Pictures) segments and transcoded independently across many workers. A 1-hour video might use 100 parallel workers, reducing transcoding time from 60 minutes to < 5 minutes.

## Summary

YouTube's architecture separates two very different problems: the upload/processing pipeline (async, batch, CPU/GPU intensive) and the serving/streaming system (sync, read-heavy, latency sensitive). The async pipeline uses message queues to decouple upload from transcoding from moderation. The serving layer uses a CDN for the vast majority of traffic, Redis for hot-path metadata and view counts, and a sharded database for comments. View counting at scale uses approximate algorithms (HyperLogLog) and periodic flush patterns to avoid write bottlenecks. The key architectural insight: video bytes and video metadata are fundamentally different problems — separate their storage and serving entirely.
