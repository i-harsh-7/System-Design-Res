# 09. 30-Day Study Plan

This plan assumes you have 1.5–2 hours per day available for study. If you have more time, accelerate through the weeks. If you have less time, extend the plan to 45–60 days — but maintain the sequencing, because later chapters build on earlier ones.

This plan is not about grinding through content passively. It is about active recall, deliberate practice, and building the habit of explaining systems out loud — which is exactly what interviews require.

---

## Before Day 1: Baseline Assessment

Before starting, spend 30 minutes taking stock of where you are.

**Attempt this question from memory:** Design a URL shortener. Set a 20-minute timer. Draw the architecture, define the API, pick a database. Then read the approach in Chapter 20's questions file.

Ask yourself:
- Did I ask about requirements and scale before designing?
- Did I choose a database and justify it?
- Did I think about what happens at 100M requests per day?
- Did I articulate any trade-offs?

Be honest. The gaps you identify now are the areas to focus on. Most first attempts reveal: (1) skipping requirements, (2) not thinking about scale, and (3) vague database choices.

## Week 1: Foundations (Days 1–7)

### Goal
Build the technical vocabulary and the mental models for networking, scalability, and databases that underpin every system design question.

---

### Day 1–2: Basics + Networking (Chapters 1–2)

**Day 1 (1.5 hrs):**
- Read Chapter 1 (System Design Basics: reliability, scalability, maintainability)
- Read Chapter 2 (Networking fundamentals: TCP/UDP, DNS, HTTP/HTTPS, WebSockets)
- Write a one-page summary of Chapter 1 in your own words (active recall)

**Day 2 (1.5 hrs):**
- Review Chapter 2 networking protocols
- Memorize the latency numbers table from Chapter 20 File 05
- Practice problem: Explain the difference between TCP and UDP, and name one system where each is the right choice. Write it out in 5 sentences.

**Checkpoint questions:**
- What is the difference between horizontal and vertical scaling?
- What happens during a DNS lookup?
- Why does HTTP/2 improve on HTTP/1.1?

---

### Day 3–4: Scalability + Databases (Chapters 3–4)

**Day 3 (1.5 hrs):**
- Read Chapter 3 (Scalability: load balancing, horizontal scaling, stateless design)
- Flashcard practice: define CAP theorem, BASE properties, ACID properties

**Day 4 (1.5 hrs):**
- Read Chapter 4 (Databases: SQL, NoSQL, sharding, replication)
- Read Chapter 20 File 06 (SQL vs NoSQL Decision Guide)
- Practice: For each of these systems, choose a database and justify it in 2 sentences — Twitter tweet storage, Uber driver location, Netflix watch history, bank account balance

**Checkpoint questions:**
- What is a database read replica, and what problem does it solve?
- What is the difference between eventual consistency and strong consistency?
- When would you shard a database, and how do you choose a shard key?

---

### Day 5–7: Caching + Load Balancing (Chapters 5–6) + First Practice Design

**Day 5 (1.5 hrs):**
- Read Chapter 5 (Caching: cache-aside, write-through, eviction policies, CDN)
- Read Chapter 6 (Load Balancing: algorithms, session affinity, health checks)

**Day 6 (1.5 hrs):**
- Review Chapter 20 File 04 (Design Patterns Reference Card) — focus on: Cache-Aside, Write-Behind, Consistent Hashing, Leader-Follower
- Memorize the storage size table from Chapter 20 File 05

**Day 7 (2 hrs) — First Practice Design:**
- Set a 45-minute timer.
- Design a "simple web application" — pick any of these: a blog platform, a task management app, a news aggregator.
- Spend 5 min on requirements, 5 min on API, 5 min on data model, 10 min on high-level design, 10 min on scaling considerations, 5 min on trade-offs.
- After the timer: review Chapter 20 File 01 (Interview Framework) and assess: where did you follow the framework? Where did you deviate?

**Week 1 retrospective (15 min):** What concepts are still fuzzy? Write them down. You will encounter them again in Week 2 with more context.

## Week 2: Core Distributed Systems (Days 8–14)

### Goal
Understand the building blocks that appear in nearly every large-scale system: distributed storage, message queues, and the consistency/availability trade-offs that govern them.

---

### Day 8–10: Distributed Systems, Storage, Message Queues (Chapters 7–9)

**Day 8 (2 hrs):**
- Read Chapter 7 (Distributed Storage: HDFS, object storage, block storage)
- Read Chapter 20 File 05 (Numbers Every Engineer Should Know) — pay attention to storage sizes and throughput numbers

**Day 9 (2 hrs):**
- Read Chapter 8 (Distributed Systems Fundamentals: consensus, leader election, replication, Paxos/Raft overview)
- Understand the difference between: synchronous replication, asynchronous replication, semi-synchronous replication. Write one paragraph on each.

**Day 10 (2 hrs):**
- Read Chapter 9 (Message Queues: Kafka, RabbitMQ, SQS — use cases, guarantees, partitioning)
- Practice: Draw a system diagram where a user uploads a video, and explain how a message queue enables async processing. What are the components? What events does the queue carry? What happens if a worker crashes mid-process?

**Checkpoint questions:**
- What is a write-ahead log and why do databases use it?
- What is Kafka's replication factor and what does it protect against?
- What is at-least-once vs exactly-once delivery, and why is exactly-once hard?

---

### Day 11–14: First Case Studies

This week, you practice applying the framework to real systems. Each case study should take 45–60 minutes.

**Day 11 (60 min): Design a URL Shortener**
- Set a timer. Go through all 6 phases of the framework.
- Core focus: Base62 encoding, database choice, caching hot short codes, handling 100M redirects/day.
- After: Read the URL Shortener entry in Chapter 20 File 03. What did you miss? What did you do well?

**Day 12 (60 min): Design Pastebin (text storage and sharing)**
- Similar to URL shortener but focus shifts to: storing variable-length text content, generating unique IDs, expiration, read-heavy optimization.
- Challenge: What happens when paste content is 10 MB? How does that change your design?

**Day 13 (60 min): Design a Notification System**
- Core focus: multi-channel delivery (push, email, SMS), async architecture, handling user preferences, rate limiting per user, retries.
- Read the Notification System entry in Chapter 20 File 03 after.

**Day 14 (90 min): Mock Interview Simulation**
- Ask a friend or use a mock interview service (Pramp, Interviewing.io) to run a full 45-minute mock.
- If no partner available: set a timer, pick a question randomly from Chapter 20 File 03, and present your solution out loud as if to an interviewer. Record yourself.
- After: honest self-assessment on each dimension from Chapter 20 File 08 (Behavioral Signals).

**Week 2 retrospective:** Which case study was hardest? Identify the underlying concept (fan-out, async processing, DB scaling) and re-read that concept in the relevant chapter.

## Week 3: Advanced Topics + Complex Case Studies (Days 15–21)

### Goal
Handle the hardest topics (consistency models, microservices, real-time systems) and practice the designs that appear most at senior/staff interviews.

---

### Day 15–17: Consistency, Reliability, Microservices (Chapters 10–12)

**Day 15 (2 hrs):**
- Read Chapter 10 (Consistency and Consensus: strong vs. eventual consistency, linearizability, vector clocks)
- Study these scenarios: Read-your-writes consistency, monotonic reads, causally consistent reads. For each: when does it matter? Which systems provide it by default?

**Day 16 (2 hrs):**
- Read Chapter 11 (Reliability and Fault Tolerance: failure modes, redundancy, chaos engineering, SLI/SLO/SLA)
- Study Chapter 20 File 04: Circuit Breaker, Saga Pattern, Outbox Pattern — these appear directly in reliability questions.

**Day 17 (2 hrs):**
- Read Chapter 12 (Microservices: service decomposition, communication patterns, service mesh)
- Practice: Take the URL shortener design from Day 11 and redesign it as a microservices architecture. What services do you create? What are the trade-offs vs. the monolith?

### Day 18–21: Complex Case Studies

**Day 18 (60 min): Design WhatsApp (Chat System)**
- Core challenges: WebSocket connections at scale, routing messages between servers, offline delivery, group messaging.
- Use the framework. Draw the connection management layer and message routing.

**Day 19 (60 min): Design Instagram (Photo Sharing + Feed)**
- Core challenges: Photo storage (S3, CDN), feed generation (fan-out), ranking/chronological sort.
- Estimate: How much storage does Instagram need per year? (Use Chapter 20 File 02 worked example.)

**Day 20 (60 min): Design Twitter (Feed + Posts)**
- Core challenge: The celebrity problem. Hybrid push/pull model.
- Practice explaining the fan-out trade-off verbally: "I chose a hybrid model because..."

**Day 21 (90 min): Mock Interview Simulation**
- Second mock interview. If using a partner, ask them to challenge one of your design decisions mid-interview.
- Focus specifically on: How do you handle the challenge? Do you update your design clearly? Do you articulate the new trade-off?

**Week 3 retrospective:** Which of the behavioral dimensions from Chapter 20 File 08 are still weak? Focus on those in Week 4.

## How to Run a Mock Interview

### Finding a Partner

- Ask a friend or colleague who is also preparing for interviews.
- Use Pramp (free, peer-to-peer system design practice).
- Use Interviewing.io (paid, with engineers from top companies).
- Use Exponent (paid, structured practice with video feedback).

### Running It Yourself (Solo)

If no partner is available:
1. Pick a question from Chapter 20 File 03 that you haven't practiced.
2. Set a 45-minute timer.
3. Open a blank sheet of paper or Excalidraw.
4. Speak out loud — narrate everything as if to an interviewer.
5. Record the audio (your phone is fine).
6. After 45 minutes: Stop. Listen to the recording. Evaluate:
   - Was I silent for more than 30 seconds at any point?
   - Did I spend 5 minutes on requirements?
   - Did I articulate trade-offs?
   - Did I cover failure modes proactively?

### The 5-Question Self-Evaluation

After every mock, answer these honestly:

1. Did I define requirements before designing?
2. Did I make at least 3 design decisions with explicit trade-offs?
3. Did I think out loud throughout?
4. Did I cover at least 2 failure modes or bottlenecks proactively?
5. Would I trust this design in production?

## The Day Before Your Interview

**The night before:**
- Do not study new material. You are not going to learn anything new in 2 hours that will meaningfully change your performance.
- Review the framework (Chapter 20 File 01) and the numbers (Chapter 20 File 05) for 30 minutes.
- Get 8 hours of sleep. This is not optional. Sleep deprivation measurably impairs the ability to reason about complex systems.

**The morning of:**
- Eat breakfast. Your brain runs on glucose.
- Do a 15-minute light review of the framework. Say it out loud once: "Requirements, API, Data Model, High-Level Design, Scale and Deep Dive, Trade-offs."
- Practice one estimation: "If 100M users each make 50 reads per day, what's the RPS?" Do it in your head.
- Have Excalidraw or your whiteboard ready before the interview starts.

**During the interview:**
- Start by writing the requirements on the board. Do not draw anything until you have confirmed the requirements.
- When you don't know something, say so and reason forward.
- When challenged, update your design — don't defend it.
- Watch the clock. 45 minutes goes faster than you think.

## If You Have Only 1 Week

One week is not enough to master system design. But if your interview is in a week:

**Day 1:** Chapter 20 File 01 (Framework) + File 02 (Estimation) — read carefully, practice once.

**Day 2:** Chapter 20 File 05 (Numbers) + File 06 (DB Guide) — memorize the tables.

**Day 3:** Chapter 20 File 04 (Patterns) + File 03 (50+ questions) — read all approaches.

**Day 4:** Design Twitter feed (45 min timed), evaluate, re-read the framework.

**Day 5:** Design WhatsApp or Uber (45 min timed), evaluate.

**Day 6:** Mock interview (full 45 min), debrief.

**Day 7:** Light review of frameworks and numbers. Sleep.

At this timeline, you will not be deep — but you will have the vocabulary, the framework, and enough pattern recognition to hold your own.

## Recommended Resources Beyond This Course

| Resource | What It Covers | When to Use |
|----------|---------------|-------------|
| *Designing Data-Intensive Applications* (Kleppmann) | Deep dive on databases, replication, distributed systems | Weeks 2–3, for deep understanding |
| *System Design Interview Vol 1 & 2* (Alex Xu) | Walkthrough of common systems | Supplemental case studies |
| *The Architecture of Open Source Applications* (free online) | How real systems are actually built | Background reading |
| Highscalability.com | Architecture breakdowns of real companies | After practicing a system, read how it's actually built |
| engineering blogs (Uber, Airbnb, Dropbox, Discord) | Real-world engineering decisions | Most valuable reading, period |

The engineering blogs are particularly valuable because they describe real decisions made by real engineers, including the mistakes and the reasoning that led to specific choices. Reading "How Discord Stores Billions of Messages" teaches you more about Cassandra than any textbook chapter.
