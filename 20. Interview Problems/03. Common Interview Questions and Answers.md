# 03. Common System Design Interview Questions and Answers

This reference covers 50+ of the most commonly asked system design questions, organized by difficulty. For each question, you will find:
- **Core challenge:** The single hardest technical problem in the design
- **Key design decision:** The most important architectural choice
- **Approach:** A concise paragraph walking through the design

Use this as a quick-review reference before interviews. For production-quality designs, each of these topics deserves hours of deeper study.

---

## Beginner Questions

These questions appear at early-career interviews or as warm-ups. They have well-known solutions and limited ambiguity.

---

### 1. Design a URL Shortener (e.g., bit.ly)

**Functional requirements:** Users submit a long URL and receive a short URL. Clicking the short URL redirects to the original. Optionally: custom aliases, link expiration, click analytics.

**Core challenge:** Generating short codes that are unique, URL-safe, and short (6–8 characters).

**Key design decision:** Hash-based vs. ID-based code generation.

**Approach:** Store URL mappings in a relational database (url_id, short_code, long_url, created_at, expires_at). Generate short codes by encoding a unique auto-increment ID using Base62 (a-z, A-Z, 0-9 = 62 chars). A 7-character Base62 code supports 62^7 = ~3.5 trillion URLs. On redirect, look up the short code in the database (with a cache layer in Redis for hot links), return an HTTP 301 (permanent) or 302 (temporary, better for analytics) redirect. For custom aliases, check uniqueness before storing. Shard by short_code hash when you exceed single-database scale.

---

### 2. Design a Key-Value Store

**Functional requirements:** PUT(key, value), GET(key), DELETE(key). Optional: TTL, range queries.

**Core challenge:** Balancing consistency, availability, and partition tolerance (CAP theorem). Deciding the storage engine.

**Key design decision:** In-memory only (Redis-style) vs. persistent (RocksDB-style).

**Approach:** For an in-memory store, use a hash map as the data structure and a linked list (or sorted set) for LRU eviction. For persistence, add a write-ahead log (WAL) that records every operation — on restart, replay the WAL. For distributed operation, shard by consistent hashing across nodes. Replication provides fault tolerance. For a simple interview, design a single-node store first, then explain how you'd distribute it.

---

### 3. Design a Parking Lot System

**Functional requirements:** Track parking spots (compact, regular, handicapped). Cars enter/exit. Display available spots. Calculate payment on exit.

**Core challenge:** Concurrency — two cars trying to claim the same spot.

**Key design decision:** How to prevent race conditions on spot assignment.

**Approach:** Model the lot as floors containing spots. Each spot has a status (AVAILABLE, OCCUPIED) and a type. On car entry, query for an available spot of the right type (with a distributed lock or optimistic locking on the spot row to prevent double-booking). Issue a ticket with spot_id, car_id, entry_time. On exit, calculate duration, apply pricing tiers (first hour free, hourly rate after), mark spot as available. For real-time spot availability display, maintain a counter per floor per spot type (increment/decrement in Redis for speed).

---

### 4. Design a Library Management System

**Functional requirements:** Users search for and borrow books. Staff adds new inventory. System tracks borrowing history and due dates. Fines for overdue books.

**Core challenge:** Inventory management — multiple copies of the same title, tracking which physical copy is with which borrower.

**Key design decision:** Separating the logical book (title, author, ISBN) from physical copies.

**Approach:** Two entities: Book (isbn, title, author, genre) and BookCopy (copy_id, isbn, status: AVAILABLE/BORROWED/RESERVED). A Loan record links a borrower (user_id) to a BookCopy (copy_id) with borrow_date and due_date. On borrow: find any available copy of the requested ISBN, create a Loan record, update BookCopy status to BORROWED — all in one transaction. Run a daily job to identify overdue loans and calculate fines. Use full-text search (Elasticsearch or PostgreSQL full-text) for book search by title/author.

## Intermediate Questions

These are the most commonly asked questions at mid-level and senior interviews. The designs require real distributed systems knowledge.

---

### 5. Design Twitter / Instagram Feed

**Functional requirements:** Users post content. Users follow other users. Users see a personalized feed of content from people they follow, sorted by recency (or relevance).

**Core challenge:** Fan-out at scale. If a celebrity with 10 million followers posts, you can't write 10 million database rows synchronously.

**Key design decision:** Fanout-on-write (push model) vs. fanout-on-read (pull model).

**Approach:** Use a hybrid model. For regular users (< 1000 followers), use fanout-on-write: when a user posts, asynchronously push the post_id into each follower's pre-computed timeline in Redis (sorted by timestamp). Feed reads are O(1) — just read the Redis sorted set. For celebrity accounts (> 1000 followers), skip fanout-on-write. When a follower requests their feed, merge their pre-computed timeline with a live query for posts from celebrities they follow. This keeps the Redis memory bounded and avoids the write explosion on celebrity posts. Kafka coordinates the async fanout workers.

### 6. Design WhatsApp (Chat System)

**Functional requirements:** One-on-one messaging. Group messaging. Message delivery status (sent, delivered, read). Push notifications for offline users.

**Core challenge:** Maintaining persistent connections at scale (100M concurrent users) and delivering messages to offline devices.

**Key design decision:** How to route messages between users on different servers.

**Approach:** Each client maintains a persistent WebSocket connection to a Chat Server. A Service Discovery / consistent hashing layer maps user_id to a specific Chat Server. When User A sends a message to User B: the message goes to User A's Chat Server, which stores it in the message database (Cassandra, partitioned by conversation_id), then looks up which server User B is connected to via a Presence Service (Redis key: user_id → server_id). If User B is online, the Chat Server forwards the message. If offline, a Notification Service pushes to APNs/FCM. Delivery receipts flow in reverse. Messages are end-to-end encrypted in the client — the server only sees ciphertext.

### 7. Design Uber / Lyft (Ride-Hailing)

**Functional requirements:** Riders request rides. Drivers indicate availability. System matches rider to nearby driver. Real-time location tracking. Fare calculation on trip end.

**Core challenge:** Location indexing — efficiently finding all available drivers within 1 km of a rider.

**Key design decision:** Geospatial indexing using geohash or quadtree.

**Approach:** Drivers continuously send GPS coordinates (every 4 seconds). Store current driver locations in Redis using geospatial indexes (Redis GEOADD/GEORADIUS). When a rider requests a ride, query for available drivers within N km radius. The matching algorithm ranks candidates by distance and driver rating, then sends a push notification to the top candidates. The first to accept gets the ride. Trip state machine: REQUESTED → MATCHED → DRIVER_EN_ROUTE → IN_PROGRESS → COMPLETED. Historical location data goes to Kafka → data warehouse for route optimization and pricing. Surge pricing is calculated by comparing supply (available drivers) to demand (open requests) per geohash cell.

### 8. Design a Notification System

**Functional requirements:** Send push notifications (mobile), emails, and SMS to users based on events. Support templates. Respect user preferences. High deliverability.

**Core challenge:** Handling millions of notifications per second during peak events (a tweet from a celebrity, a flash sale alert) without dropping messages.

**Key design decision:** Decoupled event-driven architecture with per-channel workers.

**Approach:** Build a Notification Service that accepts events via API or message queue (Kafka). A routing service reads the event, determines which users to notify and by which channels (based on user preferences stored in a DB), and enqueues channel-specific jobs. Separate workers handle each channel: Email Worker (via SendGrid/SES), Push Worker (via Firebase/APNs), SMS Worker (via Twilio). Each channel has a queue (Kafka topic or Redis queue). Use rate limiting per user to prevent spamming. Templates are stored in a DB and rendered at send time. Failed deliveries go to a dead-letter queue for retry with exponential backoff. Track delivery status in a time-series store for analytics.

### 9. Design a Rate Limiter

**Functional requirements:** Limit the number of requests from a given user/IP within a time window. Return HTTP 429 when the limit is exceeded. Configurable limits per API endpoint.

**Core challenge:** Implementing the rate limit check with sub-millisecond latency and consistency across distributed API servers.

**Key design decision:** Which algorithm — token bucket, sliding window, or fixed window?

**Approach:** Use a sliding window counter in Redis. For each request, use a Lua script (atomic in Redis) to: increment a counter for the current time window, expire old windows, check if the count exceeds the limit. Using a Lua script ensures atomicity without race conditions. Token bucket is better for bursty traffic (allows short bursts while maintaining average rate). For distributed rate limiting across multiple data centers, use Redis Cluster with local counters that sync periodically — this trades perfect accuracy for availability. Embed the rate limiter as middleware in your API gateway layer so it runs before requests reach application servers.

### 10. Design a Web Crawler

**Functional requirements:** Given a set of seed URLs, crawl the web by following links. Store page content. Respect robots.txt. Handle millions of URLs.

**Core challenge:** Avoiding infinite loops (URLs pointing back to visited pages) and politeness (not hammering a single domain).

**Key design decision:** URL frontier management — how to prioritize and deduplicate URLs to crawl.

**Approach:** Maintain a URL Frontier (priority queue of URLs to crawl) and a Visited URL store (Bloom filter for fast membership testing — "have I crawled this URL?"). Crawler workers pull from the frontier, fetch the page, extract links, store content in object storage (S3), parse and queue new URLs. Per-domain rate limiting prevents hammering single servers. Respect robots.txt by caching each domain's rules. Distribute across multiple crawler workers using a consistent hash on domain name — this keeps all requests to a given domain on the same worker (for politeness throttling). Use a Bloom filter (not a hash set) for visited URLs to keep memory bounded — accept the small false-positive rate.

### 11. Design a Search Autocomplete (Typeahead)

**Functional requirements:** As a user types, show the top 5 most popular search queries matching the prefix. Sub-100ms response time.

**Core challenge:** Prefix matching at scale with real-time popularity updates.

**Key design decision:** Trie in memory vs. database-backed search.

**Approach:** Build a trie data structure where each node represents a character prefix. At each node, store the top-K queries (sorted by frequency) that pass through that node. Query time is O(L) where L is the prefix length. Frequency data is collected from search logs and aggregated in batch (Hadoop/Spark) every few hours — the trie doesn't need to be real-time. The trie is serialized and stored in a distributed cache (Redis or a CDN), with the API tier reading from cache. For very long tail queries, fall back to Elasticsearch. For real-time suggestions (trending now), overlay a separate hot-queries tracker that logs searches to a stream processor, which updates a separate top-K structure in Redis.

### 12. Design a Distributed Cache

**Functional requirements:** GET and PUT operations. TTL support. Eviction when full. Consistent performance at scale.

**Core challenge:** Distributing the key space across nodes while handling node additions/removals without rehashing all keys.

**Key design decision:** Consistent hashing for key distribution.

**Approach:** Use consistent hashing to distribute keys across cache nodes. Each node owns a range of the hash ring. Virtual nodes (vnodes) per physical node prevent hotspots. Client-side routing: the client library computes which node owns a key and goes directly (no central coordinator). For replication, each key is replicated to the next N nodes on the ring. Eviction: LRU is standard (Redis default). Cache-aside pattern: application checks cache, on miss reads DB and writes to cache. For large values, store a pointer to S3 in the cache and serve the actual data from S3. Monitor hit rate, eviction rate, and memory utilization — a hit rate below 80% usually means the cache is too small or the eviction policy is wrong.

### 13. Design a Job Scheduler (Cron-as-a-Service)

**Functional requirements:** Users define jobs with a cron expression and a callback URL. System executes jobs at the right time. At-least-once delivery. Job history and status.

**Core challenge:** Ensuring a job fires exactly once (or at-least-once) even when scheduler nodes fail.

**Key design decision:** Using a distributed lock (ZooKeeper/Redis) to prevent duplicate execution.

**Approach:** Store job definitions in a relational database (job_id, cron_expression, callback_url, status, last_run). A Leader Scheduler (elected via ZooKeeper) scans jobs due in the next minute and enqueues them into a task queue (Kafka or a delayed queue like SQS). Worker nodes pull from the queue and make the HTTP callback. Use distributed locking per job_id to prevent two workers from running the same job simultaneously. Track execution in a job_runs table (job_id, run_id, status, started_at, completed_at). For exactly-once semantics: include a run_id in the callback URL; the worker checks if it has already processed this run_id (idempotency key). Use exponential backoff for failed callbacks.

## Advanced Questions

These appear at senior and staff-level interviews. They require deep understanding of distributed systems trade-offs.

---

### 14. Design Google Search

**Functional requirements:** Index billions of web pages. Return the most relevant results for a query in < 200ms. Handle billions of queries per day.

**Core challenge:** Building an inverted index at web scale and ranking results in real-time.

**Key design decision:** Offline index building (MapReduce) vs. real-time index updates.

**Approach:** The system has two major subsystems: Indexing and Serving. Indexing: a web crawler continuously fetches pages. A document processor extracts text, builds an inverted index (term → list of (doc_id, tf-idf score) pairs), and stores it in a distributed index. The index is partitioned by term (horizontal: different terms on different shards) and replicated. PageRank is computed offline via iterative graph processing. Serving: a query goes to a Mixer that queries multiple Index shards in parallel, each returning top-K results for their term subset, and then merges and re-ranks the results using a learned ranking model (BERT-based signals). Caching of popular query results at the CDN level cuts load dramatically.

### 15. Design YouTube

**Functional requirements:** Users upload videos. Videos are transcoded to multiple resolutions. Users stream videos. Comments, likes, subscriptions. Recommendation feed.

**Core challenge:** Video transcoding at scale (processing hours of video per second) and adaptive bitrate streaming.

**Key design decision:** Async transcoding pipeline with a message queue.

**Approach:** Upload: video goes to object storage (S3). A Transcoding Service (workers pulling from a queue) converts the raw video to multiple formats (360p, 720p, 1080p, 4K) using FFmpeg, storing outputs back in S3. CDN pre-warms popular videos by pushing them to edge nodes. Streaming uses HLS or DASH — the video is split into 2–10 second segments; the client requests segments based on measured bandwidth (adaptive bitrate). Metadata (title, description, views, likes) lives in a relational database. View counts are eventually consistent — increment a counter in Redis, batch-flush to DB every minute. Recommendation engine uses collaborative filtering on a user-video interaction graph, computed offline.

### 16. Design Netflix

**Functional requirements:** Stream high-quality video to millions of concurrent viewers. Personalized recommendation. Content management. Global availability.

**Core challenge:** Delivering video with low startup latency and minimal buffering across variable network conditions globally.

**Key design decision:** Using a custom global CDN (Open Connect) co-located at ISPs.

**Approach:** Netflix runs Open Connect Appliances (OCA) — custom CDN servers — inside ISP networks. Popular content (80% of traffic) is pre-positioned at ISPs. The remaining 20% is served from Netflix's own data centers. The client uses ABR (adaptive bitrate): starts low resolution, increases as buffer fills. If an edge node is slow, the client retries another. Microservices architecture: a separate service for streaming, recommendations, user accounts, billing. Recommendation: two-stage — offline collaborative filtering generates candidates; online ranking model re-ranks based on context (time of day, device, recent history). Chaos Engineering (the Netflix approach): deliberately inject failures to verify the system degrades gracefully.

### 17. Design Google Maps / Navigation

**Functional requirements:** Show a map. Directions between two points. Real-time traffic. ETA calculation. Search for places.

**Core challenge:** Routing at web scale — the road network graph has hundreds of millions of nodes and edges, and shortest-path algorithms are too slow to run naively.

**Key design decision:** Pre-computed routing tiles with Dijkstra's or A* over contracted hierarchies.

**Approach:** The map data is represented as a directed graph (nodes = intersections, edges = road segments with weights for distance, speed, and real-time congestion). The graph is pre-partitioned into routing tiles by geography. Contraction Hierarchies (CH) pre-process the graph: "shortcut edges" are added to skip less important nodes, making Dijkstra's run orders of magnitude faster. Real-time traffic comes from user GPS data: millions of Android/iPhone devices report speed every few seconds → aggregated into a traffic model → edge weights updated. Map tiles (visual rendering) are rasterized or vector tiles served from CDN. Place search is a combination of fuzzy text search (Elasticsearch) and geospatial proximity queries.

### 18. Design a Distributed File System (e.g., HDFS, GFS)

**Functional requirements:** Store large files (GB–TB) across many machines. High throughput sequential reads/writes. Fault tolerance against hardware failures.

**Core challenge:** Splitting files into chunks, distributing chunks across nodes, and recovering from node failures without data loss.

**Key design decision:** Master/worker architecture with chunk replication factor of 3.

**Approach:** Files are split into fixed-size chunks (64 MB is classic). A Master Node stores the file namespace (file path → list of chunk IDs) and chunk locations (chunk_id → list of ChunkServer IDs). ChunkServers store actual chunk data. Each chunk is replicated to 3 ChunkServers (in different racks for fault tolerance). Clients get chunk locations from the master, then read/write directly to ChunkServers (bypassing the master for data transfer). The master monitors ChunkServer heartbeats; if a server is missing, the master re-replicates its chunks to bring replication factor back to 3. The master is a single point of failure — mitigated by a shadow master that tails the operation log.

### 19. Design a Distributed Message Queue (e.g., Kafka)

**Functional requirements:** Producers publish messages to topics. Consumers subscribe to topics and receive messages. Messages are persisted durably. High throughput. Consumer groups for load-balanced consumption.

**Core challenge:** Delivering millions of messages per second with durability and exactly-once (or at-least-once) semantics.

**Key design decision:** Append-only log storage for both write throughput and consumer offset tracking.

**Approach:** A topic is divided into partitions (like shards). Each partition is an append-only log file on disk. Producers write to a partition's end (O(1) seek, leverages disk sequential write speed). Consumers maintain an offset (their position in the log) — advancing offset is just incrementing a number, not deleting records. Consumer groups: multiple consumers in a group each own a subset of partitions. Replication: each partition has a leader and N-1 followers. Writes go to the leader; followers replicate. A write is confirmed (acked) when N replicas have it (configurable). On leader failure, a follower becomes the new leader. Log compaction: for key-value semantics, Kafka can compact the log to keep only the latest value per key.

### 20. Design a Distributed ID Generator (e.g., Snowflake)

**Functional requirements:** Generate globally unique, sortable IDs across distributed nodes. Millisecond-granularity time ordering. High throughput (100K+ IDs/sec per node).

**Core challenge:** Generating IDs without coordination (no central sequence number) while maintaining time ordering.

**Key design decision:** Snowflake ID structure: timestamp + machine_id + sequence_number.

**Approach:** A Snowflake ID is a 64-bit integer composed of: 41 bits for timestamp (milliseconds since a custom epoch, lasts 69 years), 10 bits for machine_id (up to 1,024 nodes), 12 bits for sequence number (up to 4,096 IDs per millisecond per node). The machine_id is assigned at startup via ZooKeeper. Because the timestamp is in the most significant bits, IDs sort chronologically. Within a millisecond, the 12-bit sequence handles 4,096 IDs; if the sequence overflows, wait for the next millisecond. Clock skew is the critical failure mode — if a machine's clock goes backward, IDs could be non-monotonic. Mitigate by refusing to generate IDs when the current time is less than the last recorded time.

## How to Use This List

Do not try to memorize all 50 designs. Instead:

1. **Understand the patterns, not the answers.** "Design WhatsApp" and "Design a live chat" are the same problem at different scales. If you understand the pattern (WebSocket connections, message routing, offline delivery), you can adapt it.

2. **Group by pattern:** Rate limiting (questions 9, 22), feed/timeline (5, 15, 16), messaging (6, 30), location (7, 41, 32) — the same core design appears across many questions.

3. **Practice the 10 most common:** URL shortener, Twitter feed, WhatsApp, Uber, YouTube, web crawler, search autocomplete, distributed cache, notification system, and rate limiter. These cover 80% of what you will see.

4. **For every design, know the one trade-off.** Fan-out (push vs. pull). Consistency vs. availability. Storage vs. compute.
