# 01. System Design Interview Framework

A system design interview is an open-ended conversation. Unlike coding interviews, there is no single correct answer. What the interviewer is evaluating is your process — how you approach an ambiguous problem, how you make decisions, how you communicate your thinking, and how you handle constraints and challenges.

The framework presented here is a structured process for navigating any system design question. It is not a script to memorize. It is a thinking tool that prevents you from freezing up or wasting time on the wrong things.

---

## The RADISH Framework

The framework covers six phases, in order:

| Phase | What You Do | Time Budget |
|-------|-------------|-------------|
| **R** — Requirements | Clarify scope, scale, and constraints | 5 min |
| **A** — API Design | Define the interface your system exposes | 5 min |
| **D** — Data Model | Define the data you store and how | 5 min |
| **I** — Infrastructure (High-Level Design) | Sketch major components and data flow | 10 min |
| **S** — Scale and Deep Dive | Go deep on key components, handle bottlenecks | 15 min |
| **H** — Hard Constraints and Trade-offs | Identify failure modes, summarize trade-offs | 5 min |

Total: 45 minutes.

---

## Phase 1: Requirements (5 Minutes)

### Goal
Transform a vague prompt into a concrete, bounded problem you can design a solution for.

The interviewer gives you "Design Twitter." That is not a design problem — it is an entire company. You need to turn it into: "Design a system where users can post short text updates, follow other users, and see a personalized feed of posts from people they follow, at a scale of 300 million daily active users."

### What to Ask

**Functional requirements — what the system does:**
- "What are the core features? For Twitter: posting tweets, following users, reading the feed — should I focus on all three or prioritize the feed?"
- "Are there any features I should explicitly exclude? For example, should I design DMs, trending topics, or ads?"
- "Who are the users? Is this a consumer product or an internal tool?"

**Scale and traffic:**
- "How many daily active users are we targeting?"
- "What is the read/write ratio? Is this read-heavy like a news feed or write-heavy like a logging system?"
- "What is the expected growth rate? Are we designing for today's traffic or next year's?"
- "Are there traffic spikes — for example, a big event that drives 10x normal traffic?"

**Non-functional requirements:**
- "How important is consistency vs. availability? Is it acceptable for a user to see a slightly stale feed, or does it need to be real-time?"
- "What is the acceptable latency? Should the feed load in under 100ms, or is 1 second okay?"
- "What are the durability requirements? If we lose a message, is that acceptable?"
- "Are there geographic requirements? Multi-region? Specific compliance needs like GDPR?"

**Constraints:**
- "Are there any specific technology constraints? For example, do we need to use a particular cloud provider?"
- "Is cost a constraint? Are we optimizing for cost efficiency or performance?"

### What to Write Down

Write the requirements visibly — on the whiteboard, or as text in the shared document. This serves two purposes:
1. It confirms your understanding with the interviewer.
2. It gives you a reference throughout the rest of the interview.

**Example output from requirements phase:**

```
Functional:
- Users can post tweets (text, up to 280 chars; ignore media for now)
- Users can follow other users
- Users can view a home timeline (feed of people they follow)
- Ignore: DMs, trending, ads, notifications

Non-functional:
- 300M DAU, read:write ratio 100:1
- Feed should load in < 200ms (p99)
- Tweets don't need to be real-time — 5-10s lag is acceptable
- High availability (99.99%) — favor availability over consistency
- Data should be durable — never lose a posted tweet

Scale (rough):
- 300M DAU * 5 tweets/day read = 1.5B reads/day = ~17,000 RPS reads
- 300M DAU * 0.1 tweets/day write = 30M writes/day = ~350 WPS writes
```

### Common Mistakes in Phase 1

- **Starting to draw before finishing requirements.** The cost of a wrong assumption is 20 minutes of re-design.
- **Asking too many questions.** Focus on what actually changes the architecture. The color scheme of the UI does not.
- **Not writing down requirements.** You will forget them. So will the interviewer.
- **Asking about things that are obviously out of scope.** "Should I handle satellite connectivity?" is not a useful question for "Design Twitter."

## Phase 2: API Design (5 Minutes)

### Goal
Define the interface your system exposes. This forces you to think concretely about what data flows in and out.

API design in interviews is not about REST vs. GraphQL debates. It is about: what are the operations this system supports, and what data do they need?

### What to Define

Write 3–5 API endpoints or function signatures. For Twitter's feed:

```
POST /tweets
  Body: { user_id, content }
  Returns: { tweet_id, created_at }

GET /timeline/{user_id}
  Query params: ?limit=20&before_tweet_id=<id>
  Returns: [{ tweet_id, author_id, content, created_at }, ...]

POST /follows
  Body: { follower_id, followee_id }
  Returns: 200 OK

DELETE /follows/{follower_id}/{followee_id}
  Returns: 200 OK
```

### Why This Step Matters

Defining the API before the architecture forces you to think about:
- What data the client sends and receives (shapes your data model)
- What operations need to be fast (shapes your caching strategy)
- What operations are write-heavy vs. read-heavy (shapes your database choice)

### Common Mistakes in Phase 2

- **Skipping this step.** Many candidates skip the API and jump to architecture. This is fine if pressed for time, but defining the API ensures you don't design a system that can't actually serve its clients.
- **Going too deep on API design.** This is not an API design interview. Sketch 3–5 endpoints and move on.
- **Forgetting pagination.** Any endpoint that returns a list should have pagination. Mention it even if you don't detail it.

---

## Phase 3: Data Model (5 Minutes)

### Goal
Define what data you are storing, in what format, and with what relationships.

This step answers: "What database(s) do I need, and what does the schema look like?"

### What to Define

For each major entity, write:
- Table/collection name
- Key fields
- Primary key and any important indexes

For Twitter:

```
User: { user_id (PK), username, email, created_at }
Tweet: { tweet_id (PK), user_id (FK), content, created_at }
Follow: { follower_id, followee_id, created_at }
         Composite PK: (follower_id, followee_id)
         Index on followee_id for "who follows this person"
```

Then explicitly choose your database type and justify it:

"I'll use a relational database (PostgreSQL) for Users, Tweets, and Follows because the data is structured and relational. The follow graph is a natural many-to-many table. I'll scale reads with replicas and shard by user_id when we exceed single-node limits."

"For the pre-computed timeline cache, I'll use Redis sorted sets, with tweet_id as the member and timestamp as the score. This gives me O(log n) insertion and O(k) retrieval for the top k tweets."

### Common Mistakes in Phase 3

- **Choosing a database without justification.** "I'll use MongoDB" is not an answer. "I'll use MongoDB because the tweet schema is flexible and I expect it to evolve" is an answer.
- **Forgetting indexes.** A schema without indexes is a performance disaster waiting to happen. Always mention the indexes that support your most common queries.
- **Ignoring relationships.** If you have User and Tweet entities, you need to explain how they relate and how you retrieve tweets by user.

## Phase 4: High-Level Design (10 Minutes)

### Goal
Draw the major components and show how a request flows through the system end to end.

This is where you draw the architecture diagram. Start from the client and work downstream.

### What to Draw

1. **Client** (mobile app, web browser)
2. **DNS / CDN** (for static assets; mention it even if you don't detail it)
3. **Load Balancer** (distributes traffic to your API servers)
4. **API Servers** (stateless application servers; can scale horizontally)
5. **Primary Database(s)** (where data is durably stored)
6. **Cache** (Redis, Memcached — for hot data)
7. **Message Queue** (Kafka, RabbitMQ — for async processing)
8. **Background Workers** (consumers of the queue — feed generation, notifications, etc.)
9. **Object Storage** (S3 — for media, if applicable)
10. **Search Service** (Elasticsearch — if search is a feature)

Not every system needs all of these. Include what your system needs and leave out what it doesn't.

### How to Draw

- Use **boxes** for services and applications.
- Use **cylinders** for databases and persistent storage.
- Use **arrows** to show data flow, labeled with the operation (read, write, publish, consume).
- Label the protocol where it matters (HTTP/REST, gRPC, AMQP).

### What to Say While Drawing

Talk through each component as you add it:

"The client sends a GET /timeline request to the load balancer. The load balancer distributes to one of N stateless API servers. The API server checks the Redis timeline cache first — if it's a hit, it returns immediately. If it's a miss, it queries the timeline service, which assembles the feed from the Tweet table, writes the result back to cache, and returns it. Feed updates happen asynchronously: when a tweet is posted, the tweet write goes to the database, and a Kafka event triggers the fanout worker to push the tweet ID into each follower's timeline cache."

### Common Mistakes in Phase 4

- **Drawing too much detail too fast.** Don't draw every microservice. Show major components first. You can detail one component during the deep dive phase.
- **Drawing without narrating.** The interviewer needs to understand your diagram. Think out loud.
- **Forgetting the database.** It sounds absurd, but candidates regularly draw the entire application tier and leave the data tier as a vague box.
- **Not showing data flow direction.** Arrows without labels or direction are confusing.

## Phase 5: Scale and Deep Dive (15 Minutes)

### Goal
Go deep on the components the interviewer cares most about. Proactively identify bottlenecks and explain how you'd address them.

This is the most important phase for senior candidates. The interviewer will either pick a component to go deep on, or ask "what breaks when you scale this to 10x?"

### How to Approach Deep Dives

When the interviewer asks about a specific component, use this pattern:
1. **Restate the problem context.** "The feed generation is the most read-heavy component — 17,000 RPS."
2. **Identify the bottleneck.** "The bottleneck is the database query to assemble the feed — joining Tweet and Follow tables for each request."
3. **Propose the solution.** "I'd pre-compute the feed using a fanout-on-write approach..."
4. **Explain the trade-off.** "The downside is storage — each tweet gets written to N timelines. For a celebrity with 10M followers, one tweet means 10M writes."
5. **Handle the edge case.** "For celebrity accounts, I'd use a hybrid: pre-compute feeds for users with < 1000 followers, and do a fanout-on-read for users with > 1000 followers."

### Bottlenecks to Proactively Identify

Even if the interviewer doesn't ask, mention at least two or three:

- **Database read bottleneck:** "The timeline read will hit the database hard. I'd cache pre-computed timelines in Redis."
- **Write amplification (fanout):** "When a user with 10M followers tweets, we'd have 10M cache writes. I need to handle celebrity accounts differently."
- **Single point of failure:** "The primary database is a SPOF. I'd add a replica with automatic failover."
- **Hot partition:** "If I shard by user_id, celebrity users will create hot partitions. I'd use a composite shard key."

### Common Mistakes in Phase 5

- **Waiting for the interviewer to identify all bottlenecks.** Proactively finding issues is a strong signal.
- **Proposing solutions without explaining why.** "I'd add Redis" is not as good as "I'd add Redis to cache the top-N timeline entries per user because the timeline read is our hottest path at 17K RPS and most reads are for the same 20 tweets."
- **Ignoring operational complexity.** More components means more things to operate, monitor, and debug. Acknowledge this.

---

## Phase 6: Hard Constraints and Trade-offs (5 Minutes)

### Goal
Summarize the key trade-offs in your design and revisit the original non-functional requirements.

This phase shows that you understand your design is not perfect — it is the best fit for the given constraints.

### What to Cover

Go back to the non-functional requirements you wrote in Phase 1 and confirm you addressed each one:

| Requirement | How We Addressed It |
|-------------|---------------------|
| Feed latency < 200ms p99 | Pre-computed feed in Redis; cache hit returns in < 5ms |
| High availability (99.99%) | Database replicas, multi-AZ deployment, API servers stateless |
| Data durability | Database with WAL, replicated to at least one standby |
| Eventual consistency for feed (5-10s lag okay) | Fanout happens asynchronously via Kafka; lag is acceptable |

Then summarize the biggest trade-off you made:

"The biggest trade-off in this design is storage vs. latency. Pre-computing timelines gives us sub-10ms feed reads, but it multiplies storage by the average follower count. For 300M DAU with 300 average followers, storing 20 tweet IDs per timeline is manageable — about 360GB. But it does mean every tweet write has a fanout cost proportional to follower count."

### Common Mistakes in Phase 6

- **Skipping this phase.** Many candidates run out of time. Budget the last 5 minutes explicitly.
- **Defending your design instead of acknowledging trade-offs.** The interviewer knows your design isn't perfect. They want to see that you know it too.
- **Introducing brand-new components in the last 5 minutes.** This is the summary phase, not the design phase. Don't suddenly add a feature you didn't design.

## The 45-Minute Timeline at a Glance

```
00:00 - 05:00  Requirements Clarification
               Ask about features, scale, non-functional requirements
               Write down what you agree on

05:00 - 10:00  API Design
               Define 3-5 key endpoints
               Note read vs. write operations

10:00 - 15:00  Data Model
               Define entities, schema, indexes
               Choose and justify database type(s)

15:00 - 25:00  High-Level Design
               Draw the full system diagram
               Walk through a complete request end-to-end

25:00 - 40:00  Scale and Deep Dive
               Interviewer picks component(s) to go deep on
               Proactively identify and solve bottlenecks

40:00 - 45:00  Trade-offs Summary
               Map each NFR to your design decision
               State the biggest trade-off clearly
```

## Framework Adaptation by Interview Style

**If the interviewer is very hands-off (Google-style):** Drive all six phases yourself. Check in periodically — "I'm going to start the high-level design now, does that sound right?" This prevents you from spending too much time in any one phase.

**If the interviewer interrupts frequently (Meta-style):** Be flexible. If they want to go deep on the database in minute 8, go with it. The framework is a guide, not a rigid script.

**If you're running out of time:** Compress Phases 2 and 3. Mention the API and data model briefly ("I'd model this with a User table and a Tweet table in Postgres, with these key indexes...") and move to the architecture.

**If you get stuck:** Say "I'm going to think through this for a moment" and use first principles. "This is a write-heavy system, which means my bottleneck is probably on the write path. The options are to buffer writes in a queue, to shard the database, or to use a write-optimized database like Cassandra. Given the query patterns, I'd lean toward..."

---

*The framework is a tool for organizing your thinking. The best system design interviews feel like a conversation between two engineers solving a real problem — not a recitation of a memorized template.*
