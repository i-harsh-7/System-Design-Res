# 02. Capacity Estimation Cheat Sheet

Back-of-the-envelope calculations are a standard part of system design interviews. Interviewers ask them to verify that you can reason quantitatively about scale — that when you say "I'd shard the database," you have some sense of why a single node won't work, and when you say "I'd cache the feed," you have a rough idea of how much memory that requires.

You don't need exact numbers. You need to be within an order of magnitude, show your reasoning, and use round numbers that make the arithmetic easy.

---

## Numbers to Memorize

### Latency Numbers

These are the numbers that Jeff Dean's famous latency table popularized. Every system design engineer should have these in memory.

| Operation | Latency | Notes |
|-----------|---------|-------|
| L1 cache reference | 1 ns | On-chip, fastest possible |
| Branch misprediction | 3 ns | CPU pipeline flush |
| L2 cache reference | 4 ns | Still on-chip |
| L3 cache reference | 10 ns | Shared across cores |
| Mutex lock/unlock | 17 ns | OS kernel call |
| Main memory (RAM) reference | 100 ns | 100x slower than L1 |
| Compress 1KB with Snappy | 3,000 ns = 3 µs | |
| Read 1MB sequentially from RAM | 9,000 ns = 9 µs | ~1 GB/s throughput |
| Read 4KB randomly from SSD | 150,000 ns = 150 µs | |
| Read 1MB sequentially from SSD | 1,000,000 ns = 1 ms | |
| Round trip within same datacenter | 500,000 ns = 500 µs | 0.5 ms |
| Read 1MB sequentially from HDD | 2,000,000 ns = 2 ms | |
| Disk seek (HDD) | 10,000,000 ns = 10 ms | Random I/O killer |
| Round trip from US East to US West | 30,000,000 ns = 30 ms | |
| Round trip US to Europe | 80,000,000 ns = 80 ms | |
| Round trip US to Australia | 150,000,000 ns = 150 ms | |
| TCP packet retransmit | 1,000,000,000 ns = 1–3 s | |

**Key takeaways for system design:**
- RAM is 100x faster than SSD. Caching in memory vs. hitting disk is a 2-3 order of magnitude difference.
- Network within a datacenter (~0.5ms) is 60x faster than cross-continent (~30ms). Co-locating services matters.
- HDD random reads (10ms) are 100x slower than sequential reads (0.1ms). This is why databases avoid random I/O.
- Redis (in-memory) can respond in under 1ms. PostgreSQL on SSD typically responds in 1–10ms for indexed queries.

## Estimation Formulas

### QPS (Queries Per Second)

```
QPS = Daily Active Users × Actions Per User Per Day / Seconds Per Day

Seconds per day = 86,400 ≈ 100,000 (round up for easy math)
                           (use 86,400 for precision, 10^5 for estimates)
```

**Peak QPS:** For most consumer systems, peak is roughly 2–3x average QPS. If your average is 10K RPS, plan for 20–30K RPS at peak.

### Storage Per Year

```
Storage/year = Daily writes × Average record size × 365

Daily writes = DAU × Write events per user per day
```

### Bandwidth

```
Bandwidth = Requests per second × Average response size

For read bandwidth: QPS × Avg response size
For write bandwidth: WPS × Avg request size
```

## Worked Examples

### Example 1: Twitter — QPS and Storage

**Given assumptions:**
- 300 million DAU
- Average user reads 100 tweets/day, writes 0.1 tweets/day
- Average tweet size: 300 bytes (text only)
- Keep data for 5 years

**Read QPS:**
```
Read QPS = 300M × 100 / 100,000
         = 30,000,000,000 / 100,000
         = 300,000 RPS = 300K RPS
```

That is 300,000 read requests per second on average. Peak could be 600K–900K RPS. This confirms you need a distributed cache (Redis cluster) — no single database handles 300K QPS.

**Write QPS:**
```
Write QPS = 300M × 0.1 / 100,000
          = 30,000,000 / 100,000
          = 300 WPS
```

300 writes/second is very manageable — a single well-tuned PostgreSQL instance handles 5,000+ WPS. You don't need to shard writes on day one.

**Tweet storage per year:**
```
Tweets per day = 300M × 0.1 = 30 million tweets/day
Storage per day = 30M × 300 bytes = 9 GB/day
Storage per year = 9 GB × 365 ≈ 3.3 TB/year
Storage for 5 years = ~16.5 TB
```

16.5 TB is large but not extreme. A few database nodes with SSD storage handles this. However, if you add media (photos, videos), the storage numbers explode — see the Instagram example below.

**Bandwidth:**
```
Read bandwidth = 300K RPS × 300 bytes = 90 MB/s = ~720 Mbps
```

720 Mbps is well within a single 10 Gbps network link. This is not a bandwidth bottleneck.

**Conclusion:** Twitter is a read-heavy, cache-friendly system. The read QPS (300K) demands a distributed cache. Writes (300 WPS) are trivial. Storage (16 TB over 5 years, text only) is manageable.

### Example 2: Instagram — Photo Storage

**Given assumptions:**
- 500 million DAU
- Average user uploads 1 photo per week = 0.14 photos/day
- Average photo size: 3 MB (compressed)
- Average photo metadata: 1 KB
- Keep photos indefinitely (or 10 years)

**Photo uploads per day:**
```
Daily uploads = 500M × 0.14 = 70 million photos/day
```

**Storage per day:**
```
Photo storage/day = 70M × 3 MB = 210 TB/day
Metadata storage/day = 70M × 1 KB = 70 GB/day
```

**Storage per year:**
```
Photo storage/year = 210 TB × 365 = ~76.6 PB/year
Metadata/year = 70 GB × 365 = ~25 TB/year
```

**Storage for 10 years:**
```
Photo storage = ~766 PB ≈ 0.8 EB
```

**Conclusions:**
- Photo storage at 76 PB/year requires object storage (S3, Google Cloud Storage). You cannot store this on database servers.
- You need a CDN to serve photos. At 500M DAU each viewing 20 photos/day, that's 10 billion photo loads/day = ~115,000 photo requests/second. Serving this without a CDN would require thousands of origin servers.
- Metadata (user_id, location, timestamp, tags) at 25 TB/year is manageable in a relational database or Cassandra.

### Example 3: WhatsApp — Message Throughput

**Given assumptions:**
- 2 billion registered users, 500 million DAU
- Average user sends 40 messages/day
- Average message size: 100 bytes (text), 10% of messages are media (avg 500 KB)
- Messages stored for 30 days (or until delivered)

**Messages per day:**
```
Messages/day = 500M × 40 = 20 billion messages/day
```

**Message throughput:**
```
Average messages/second = 20B / 100,000 = 200,000 messages/sec
Peak messages/second = ~600,000 messages/sec (3x average)
```

200,000 messages/second is why WhatsApp runs on a custom Erlang-based server (Ejabberd). A single Kafka broker can handle this. A cluster of 10 brokers provides headroom.

**Text message storage per day:**
```
Text messages/day = 20B × 0.9 = 18B
Text storage/day = 18B × 100 bytes = 1.8 TB/day
```

**Media message storage per day:**
```
Media messages/day = 20B × 0.1 = 2B
Media storage/day = 2B × 500 KB = 1 PB/day
```

**30-day retention:**
```
Text: 1.8 TB × 30 = 54 TB
Media: 1 PB × 30 = 30 PB
```

**Connections:**
```
Concurrent active connections = 500M users × (fraction online at peak)
Assume 20% of DAU online simultaneously = 100M concurrent connections
```

100 million concurrent persistent connections (WebSocket or long-polling) is the core challenge for WhatsApp. At 50K connections per server, you need 2,000 servers just to maintain connections.

### Example 4: YouTube — Storage and Bandwidth

**Given assumptions:**
- 2 billion logged-in users/month, 500 million DAU
- 500 hours of video uploaded per minute
- Average video resolution: 1080p
- Average video file size: 1 GB per hour of video (original), compressed to 4 different quality levels (360p, 720p, 1080p, 4K) at ~0.5x each
- Average video viewing: 30 minutes/day/DAU

**Upload storage per day:**
```
Hours uploaded per day = 500 hours/min × 60 min/hour × 24 hours/day
                       = 720,000 hours/day

Raw storage/day = 720,000 hours × 1 GB/hour = 720 TB/day

Compressed versions (4 qualities at 0.5 GB/hour each) = 720,000 × 4 × 0.5 GB
                                                        = 1,440 TB/day = ~1.4 PB/day
```

**Viewing bandwidth:**
```
Views/day = 500M × 30 min / 10 min avg video = 1.5B views/day
Video bitrate at 1080p ≈ 5 Mbps

Concurrent viewers (peak, 1/3 of DAU) = ~167M users
Bandwidth = 167M × 5 Mbps = 835 Tbps = 835,000 Gbps
```

This is why YouTube needs one of the world's largest CDN networks. No single datacenter serves 835 Tbps. Content must be cached at edge nodes close to viewers.

## Interview Tips for Estimation

### Round Everything

In an interview, use round numbers. Do not calculate 300,234,187 / 86,400. Instead, use 300M / 100K = 3,000. The goal is an order of magnitude, not accounting precision.

**Useful round numbers:**
- Seconds per day: 100,000 (actually 86,400 — 86K is close enough)
- Seconds per month: 3,000,000
- Seconds per year: 30,000,000

### Show Your Reasoning

Write every step. The interviewer cares more about your reasoning than your answer. "I assumed 10% of users are active at any given time because the system is consumer-facing and usage is bursty" is more valuable than getting the exact number right.

### State Your Assumptions Explicitly

"I'm assuming average photo size is 3 MB compressed. Raw would be larger, but Instagram compresses on upload." If your assumption is wrong, the interviewer will correct you. That is fine — it shows you can reason from evidence.

### Tie Estimates to Design Decisions

An estimate is not useful in isolation. Always connect it to a design decision:

"300K RPS on the read path means a single database will be our bottleneck. We need a distributed cache — Redis cluster — to serve the majority of reads without hitting the database."

"76 PB of photo storage per year means we absolutely cannot store photos in a relational database. We need object storage (S3 or equivalent)."

### Use the 80/20 Rule

Focus your estimates on the components where scale actually matters. If text metadata is 25 TB/year but media is 76 PB/year, spend your estimation time on the media path.

| Metric | Small (Startup) | Medium | Large (FAANG-scale) |
|--------|-----------------|--------|---------------------|

| Database nodes | 1–2 | 5–20 | 100s–1000s |
| Storage | GB | TB | PB–EB |
| Servers | 1–10 | 10–100 | 1K–100K |
