# 05. Numbers Every Engineer Should Know

These are the reference numbers that come up constantly in system design interviews and in real engineering work. Knowing them cold lets you make quantitative design decisions instantly, rather than hand-waving. You don't need them to 5 significant figures — you need them to one order of magnitude, and you need to understand what they imply.

---

## Latency Numbers

### The Latency Hierarchy

| Level | Operation | Latency | Compared to L1 |
|-------|-----------|---------|----------------|
| CPU | L1 cache reference | 1 ns | 1x |
| CPU | L2 cache reference | 4 ns | 4x |
| CPU | L3 cache reference | 10 ns | 10x |
| CPU | Branch misprediction penalty | 3–5 ns | 3–5x |
| CPU | Mutex lock/unlock | 17 ns | 17x |
| Memory | Main RAM access | 100 ns | 100x |
| Compression | Compress 1 KB (Snappy) | 3,000 ns = 3 µs | 3,000x |
| Memory | Read 1 MB sequentially from RAM | 9,000 ns = 9 µs | 9,000x |
| Storage | Read 4 KB randomly from SSD | 150,000 ns = 150 µs | 150,000x |
| Network | Round trip within same datacenter | 500,000 ns = 0.5 ms | 500,000x |
| Storage | Read 1 MB sequentially from SSD | 1,000,000 ns = 1 ms | 10^6x |
| Storage | HDD disk seek (random) | 10,000,000 ns = 10 ms | 10^7x |
| Network | Round trip US East → US West | 30,000,000 ns = 30 ms | 3×10^7x |
| Network | Round trip US → Europe | 80,000,000 ns = 80 ms | 8×10^7x |
| Network | Round trip US → Australia | 150,000,000 ns = 150 ms | 1.5×10^8x |
| Retry | TCP packet retransmit | 1–3 s | 10^9x |

### What These Numbers Mean for System Design

**RAM vs. SSD (100 ns vs. 150,000 ns = 1,500x difference)**

If you need to serve 100,000 requests/second, and each request needs one piece of data:
- From RAM: 100,000 × 100 ns = 10 ms total CPU time → easy
- From SSD: 100,000 × 150,000 ns = 15,000 ms = 15 seconds → impossible without caching

This is why Redis (in-memory) can handle 1 million ops/sec and PostgreSQL on SSD typically handles 5,000–20,000 QPS. The cache is not a nice-to-have — it is a necessity at scale.

**Intra-datacenter vs. cross-continent (0.5 ms vs. 150 ms = 300x difference)**

A mobile user in Sydney calling an API server in New York has 150 ms of irreducible latency before your code even runs. This is why CDNs, edge computing, and multi-region deployments exist.

If you want p99 latency of 100 ms for a global service, your application code and database must complete in under 100 ms minus network latency. For a Sydney user hitting a New York server, there is literally zero budget left for your code. You must serve from a regional endpoint.

**HDD seek vs. SSD read (10 ms vs. 0.15 ms = 67x difference)**

This is why databases moved to SSDs. A PostgreSQL table scan that requires 10,000 random disk seeks takes:
- HDD: 10,000 × 10 ms = 100 seconds (effectively unusable without indexes)
- SSD: 10,000 × 0.15 ms = 1.5 seconds (painful but survivable)
- RAM: 10,000 × 0.1 µs = 1 ms (fast)

Indexes matter because they convert random seeks into sequential reads.

## Throughput Numbers

### Storage Throughput

| Medium | Sequential Read | Sequential Write | Random Read (4K blocks) |
|--------|----------------|------------------|------------------------|
| HDD (7200 RPM) | 100–150 MB/s | 100–150 MB/s | ~0.5 MB/s |
| SSD (SATA) | 500–550 MB/s | 450–500 MB/s | 100–300 MB/s |
| NVMe SSD | 3,500 MB/s | 3,000 MB/s | 700 MB/s |
| RAM (DDR4) | 40,000 MB/s | 40,000 MB/s | 40,000 MB/s |

**Key insight:** For databases and storage systems, sequential I/O is vastly more efficient than random I/O. This is why:
- Kafka uses sequential append-only writes (fast as RAM-level throughput on SSD)
- B-tree indexes reduce random I/O compared to full table scans
- LSM trees (used by Cassandra, RocksDB) convert random writes into sequential writes via compaction

## Why These Numbers Matter for Design Decisions

### RAM Size → Cache Strategy

A typical server has 64–256 GB of RAM. Redis can hold:
- At 500 bytes/entry: 64 GB ÷ 500 B = ~130 million entries per server
- Twitter's 250M DAU × one timeline (20 tweet IDs × 8 bytes = 160 bytes): 40 GB for all timelines
- This fits in RAM. Pre-computing timelines is feasible.

### Network Bandwidth → CDN Necessity

A single 10 Gbps link delivers 1.25 GB/s.
- YouTube serves 250M hours/day of video. At 5 Mbps average: 250M × 3600 × 5 Mbps / 8 = ~562 PB/day of bandwidth.
- A single 10 Gbps link could serve 1.25 GB/s × 86,400 s = ~108 TB/day.
- You'd need 562 PB / 108 TB = ~5,200 dedicated 10 Gbps links — i.e., a CDN with thousands of edge nodes.

### Database Throughput → Sharding Threshold

PostgreSQL handles ~10,000 QPS per node. If your system needs:
- < 10K QPS: single node
- 10K–100K QPS: read replicas (3–10 replicas)
- 100K–1M QPS: sharding (10–100 shards)
- > 1M QPS: distributed systems (Cassandra, DynamoDB)

### Latency Budget → Architecture Decisions

If your SLA is p99 < 100ms:
- Cross-US network: 30ms → 70ms budget for application
- Single DB query (indexed): 5–10ms → 60ms budget for everything else
- Two DB queries: 20ms → 50ms budget
- If you have more than 2 DB queries in the critical path, you need to cache or pre-compute
